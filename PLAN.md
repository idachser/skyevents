# План: собственный сервис расчёта небесных событий с API

## Цель

Заменить внешний iCal-фид in-the-sky.org собственным сервисом, который
рассчитывает события астрономически (эфемериды, без сети) и отдаёт их по
HTTP API. Сервис разрабатывается **сразу в отдельном репозитории**
(рабочее имя — `skyevents`); этот репозиторий остаётся репозиторием
бота, связь между ними — только API-контракт и Docker-образ.

Побочные выгоды:

- снимается зависимость от неофициального фида без SLA и лицензионное
  ограничение «некоммерческое использование с атрибуцией»;
- события получают структурированные параметры (тип, тела, расстояние,
  элонгация…) вместо готового английского текста → тексты можно
  рендерить шаблонами на любом языке (русская локализация бота);
- становится реализуемым отложенный пункт из `PLAN.md` репозитория бота
  (`astro_bot`) — фильтр видимости события с локации пользователя
  (высота светила считается из тех же эфемерид).

## Ключевые решения

- **Движок: Skyfield + эфемериды JPL DE440s** (`de440s.bsp`, ~32 МБ,
  покрывает 1849–2150). Skyfield — чистый Python (MIT), работает офлайн,
  в `skyfield.almanac` уже есть фазы Луны, сезоны, противостояния и
  соединения; `skyfield.searchlib` (find_minima/find_maxima/find_discrete)
  закрывает остальные поиски. Альтернативы отклонены: PyEphem устарел,
  Astropy — слишком низкоуровневый для поиска событий.
- **Событие = данные, не текст.** Модель:
  `uid` (детерминированный: `{type}:{тела}:{дата}`), `type`,
  `dt_utc` (момент пика, ISO-8601), `bodies`, `params` (JSON: разделение
  в градусах, дистанция в км, элонгация, звёздная величина…).
  Порядок тел в uid — канонический (фиксированный ранг: Солнце, Луна,
  планеты от Меркурия наружу, затем звёзды), иначе `moon-venus` и
  `venus-moon` дали бы разные uid одному событию; закрепить в `make_uid`
  и тестах. Известное ограничение: у события с пиком у полуночи UTC
  перегенерация может сдвинуть дату и тем самым uid — для будущих
  событий дубль уберёт чистка синка (этап 6), для прошедших редкий
  дубль принимаем.
  Тексты (`summary`/`description`, en + ru) рендерятся шаблонами по типу —
  на стороне сервиса, параметром `lang`.
- **Отдельный репозиторий с первого коммита.** Никаких импортов между
  ботом и сервисом; бот знает только `SKYEVENTS_URL`. Сервис деплоится
  своим `docker-compose.yml` (образ из GHCR, собранный его же CI),
  независимо от бота; общаются по имени сервиса через общую external-сеть
  `astronet`.
- **Python 3.12+, FastAPI + uvicorn.** Ограничение «3.11 из-за aiogram 2»
  касается только бота; сервис от него свободен.
- **Хранилище сервиса**: собственный SQLite-кеш «год → события».
  Генерация года выполняется фоном при старте и по расписанию (текущий
  год + следующий в декабре, как сейчас в боте); API читает только из
  кеша и явно сообщает границы покрытия.

## Этап 0. Спайк: проверка точности

Спайк — первым делом и срочно: фид отдаёт события только вперёд от
текущей даты, каждый месяц промедления сокращает базу сравнения
(первая половина 2026 уже недоступна — разве что из накопленной БД
бота).

- [x] Скрипт (`spike/` в новом репозитории), который генерирует Skyfield'ом
      события и диффает их с фидом in-the-sky.org **по всем типам
      этапа 2 за весь доступный период** (остаток 2026 + 2027),
      категоризуя расхождения: есть у нас /
      нет в фиде, есть в фиде / нет у нас, сдвиг времени. Полный дифф —
      прямой ответ на главный риск («состав не совпадёт один в один»).
      Фид скрипт скачивает сам в gitignored-каталог — коммитить его
      целиком нельзя (© Dominic Ford). Запуск: `uv run python -m
      spike.diff`, отчёт — `data/feed/report.txt`.
- [x] Сравнивать одноимённые определения: у in-the-sky для пары тел два
      события — «conjunction» (равенство прямых восхождений) и «close
      approach» (минимум углового разделения) с разным временем; наш
      `find_minima` соответствует close approach. Подтверждено диффом:
      RA-соединения смещены относительно наших минимумов на часы
      (медиана ~1.7 ч), это разные события — не генерируем их.
- [x] Критерий: расхождение моментов ≤ нескольких минут для фаз/сезонов,
      состав событий-сближений совпадает по дням. По результатам —
      зафиксировать допуски в тестах этапа 2 и уточнить пороги сближений.

Результаты диффа (2026–2027, отчёт `data/feed/report.txt`) и принятые
допуски для тестов этапа 2 (допуск ≈ 2× наблюдаемый максимум):

| Тип               | Медиана/макс |dt|   | Допуск в тестах        |
|-------------------|---------------------|------------------------|
| фазы Луны         | 0.5 / 1.4 мин       | ≤ 3 мин                |
| сезоны            | 4.1 / 5.3 мин       | ≤ 10 мин               |
| апсиды Луны       | 7.1 / 17.4 мин      | ≤ 35 мин               |
| планета–Солнце    | 8.1 / 34.8 мин      | ≤ 70 мин               |
| элонгации         | 3.2 / 8.5 ч         | ≤ 12 ч (см. ниже)      |
| сближения         | 0.3 мин / 3.9 ч     | тот же день, ≤ 8 ч     |
| лунные затмения   | 1.0 / 1.1 мин       | ≤ 3 мин                |
| солнечные затмения| 0.7 / 1.1 мин       | ≤ 3 мин                |
| метеорные потоки  | 9.4 / 12.3 ч        | ≤ 1 сутки (см. ниже)   |

- Состав 1:1 по всем типам, кроме сближений и потоков (ниже).
- Элонгации: часы расхождения — определение фида отличается от
  геоцентрического максимума углового разделения; сам состав 14/14.
  В тестах дополнительно проверять величину элонгации в градусах
  (Меркурий 18–28°, Венера 45–47.5°).
- Сближения: наши 197 против 75 у фида. Фид курирует состав: (а) пары
  Луна–Уран/Нептун не публикует вовсе (тусклые планеты), (б) события
  у соединения с Солнцем опускает (у нас Венера–Марс 0.17° в янв 2026 —
  в фиде нет, пара невидима). Решение — пороги по классам пар плюс
  фильтр наблюдаемости, см. уточнение в этапе 2.
- Потоки: наши моменты сдвинуты на ~полсуток — солнечные долготы пиков
  в спайке взяты по памяти и неточны; Южные Тауриды вообще не совпали
  (у IMO пик ~10 окт, λ☉≈197°, а не 223°). Каталог этапа 2 выверить по
  фиду; состав определяется нашим каталогом (фид даёт ~26 потоков).

## Этап 2. Генераторы событий

Каждый генератор — функция `год → list[Event]`, покрытая тестами с
допусками из этапа 0. По убыванию ценности для бота:

- [x] Предпосылка для тестов: полный DE440s в CI недоступен (тесты
      офлайн), а генераторы без эфемерид не работают. Закоммитить
      вырезку `python -m jplephem excerpt` на ~2025–2030 (порядка
      мегабайта) в `tests/data/`; тесты генераторов используют её,
      прод — полный файл. Обновить конвенцию в CLAUDE.md.
- [x] Фазы Луны (новолуние, четверти, полнолуние) — `almanac.moon_phases`.
- [x] Равноденствия и солнцестояния — `almanac.seasons`.
- [x] Перигей/апогей Луны — экстремумы расстояния Земля–Луна.
- [x] Противостояния и соединения планет с Солнцем, нижние/верхние
      соединения Меркурия и Венеры — `almanac.oppositions_conjunctions`.
- [x] Наибольшие элонгации Меркурия и Венеры — максимумы элонгации.
- [x] Сближения — минимумы углового разделения; генерируем только close
      approach (минимум), отдельное событие «conjunction» по равенству
      прямых восхождений, как у in-the-sky, не дублируем. Пороги — по
      классам пар (уточнены по диффу этапа 0): Луна–яркая планета
      (Меркурий…Сатурн) 7° (как `maxdiff=7` в фиде); любая пара с
      Ураном или Нептуном 1° (фид пары Луна–Уран/Нептун не публикует
      вовсе — ежемесячные сближения 4–6° с тусклой планетой это шум);
      планета–планета 2.5°. Плюс фильтр наблюдаемости: пару с
      элонгацией от Солнца < 15° не публиковать (фид так делает —
      Венера–Марс 0.17° в янв 2026 у соединения в фиде отсутствует);
      элонгацию класть в `params`.
- [x] Лунные затмения — `skyfield.eclipselib.lunar_eclipses`
      (модуль помечен экспериментальным — закрепить версию Skyfield
      в lockfile и накрыть тестами на известных затмениях).
- [x] Солнечные затмения — поиск в окрестности новолуний по угловому
      разделению Солнце–Луна; порог — сумма видимых радиусов **плюс
      горизонтальный параллакс Луны** (~0.95°), иначе геоцентрический
      критерий пропустит большинство частных затмений, видимых только
      с части поверхности Земли. Тип (полное/кольцеобразное/частное) —
      по геометрии, но помнить: из геоцентра тип центрального затмения
      определяется ненадёжно (отношение видимых радиусов надо брать для
      наблюдателя на поверхности; гибридные затмения — пограничный
      случай по определению). В `params` класть сырые величины
      (минимальное разделение, отношение радиусов), тип — приближённо;
      в тестах допустить расхождение на известных гибридных затмениях.
- [x] Метеорные потоки — статический каталог (рабочий список IMO:
      название, солнечная долгота пика, ZHR); момент пика в
      конкретном году считается из солнечной долготы. Важно: долготы
      IMO заданы в эклиптической долготе **J2000**, не равноденствия
      даты (калибровка по фиду это подтвердила: долготы моментов фида
      в J2000-фрейме дают в точности круглые значения IMO — Персеиды
      140.0, Геминиды 262.2; счёт во фрейме даты сдвигал бы пики на
      ~0.37° ≈ 9 часов). Каталог выверен по фиду, совпадение ≤ 2 мин.
      Радиант в каталог не включён — добавить, когда бот возьмётся за
      фильтр видимости (фаза 2).
- [x] Стояния планет (переход к попятному движению и обратно) —
      смена знака скорости видимой эклиптической долготы. Важно:
      именно долготы, не прямого восхождения — у Сатурна в 2026 эти
      два определения расходятся на 27 часов, потому что вблизи
      равноденствий проекция на экватор искажает скорость, проходящую
      через ноль. По той же причине момент принципиально мягкий
      (аберрация и выбор равноденствия сдвигают его на десятки минут);
      берём видимую долготу равноденствия даты — классическое
      определение, совпало с эфемеридными публикациями до минуты по
      двум стояниям Меркурия 2026.
      Вторая ловушка: около соединения планета уходит за диск Солнца, и
      гравитационное отклонение света в Skyfield там расходится — guard
      в `relativity.py` зануляет отклонение лишь при совпадении в
      пределах 1″, а диск Солнца ~950″. У Урана в 2029-м (элонгация
      0.01°) долгота дрожит на угловые минуты, знак скорости скачет и
      рождаются четыре ложных стояния за 2.5 часа. Отсекаем стояния с
      элонгацией < 1°: зона сбоя ≲0.1°, а ближайшее настоящее стояние —
      Меркурий на 14.75°. Чередование r/d такой дребезг не ловит
      (переходы идут парами) — ловит счёт против синодического периода,
      поэтому в тестах живёт проверка на кластеры. `planet_sun` тем же
      сбоем не задет, хотя соединения Урана попадают ровно в зону:
      момент там ищется по разности долгот планета−Солнце, которая
      растёт на ~1°/сутки, и дрожание знак не переворачивает —
      проверено, apparent и astrometric дают тот же момент до секунды.
- [ ] (Опционально, фаза 2) Покрытия Луной ярких звёзд и планет,
      перигелий/афелий Земли, максимальный блеск Венеры.

Кометы и астероиды вынесены в этап 7 — им нужны орбитальные элементы
MPC, а не эфемериды DE440s.

Замечание по методике этапа 0: спайк (`spike/feedparse.py`) отбрасывал
из фида все типы вне списка этапа 2, поэтому недостающие категории не
попадали в дифф и пропуск стояний вскрылся только на проде. Оставшиеся
отброшенные типы — покрытия, «well placed», дихотомия — либо в списке
фазы 2 выше, либо сознательно не нужны боту; отдельно свериться с
фидом, если добавится ещё одна категория.

## Этап 4. API

- [x] `GET /v1/events?from=YYYY-MM-DD&to=YYYY-MM-DD&types=...&lang=ru|en`
      — основной эндпоинт (полуинтервал по UTC). Валидация:
      `from <= to`, ограничение ширины окна (≤ 400 дней).
- [x] Явный контракт покрытия: кеш хранит только сгенерированные годы,
      и «пусто, потому что не считали» не должно выглядеть как «событий
      нет» — поле `coverage` в ответе: пересечение запрошенного окна
      со сгенерированными годами (null, если не пересекается); события
      отдаются только из покрытой части окна.
- [x] `GET /health` — для compose healthcheck и CI smoke-теста.
- [x] (Опционально) `GET /v1/calendar.ics[?year=&lang=]` — совместимость с
      форматом текущего фида: первый шаг переключения бота сводится к
      подмене URL фида (сейчас `ICS_FEED_URL` захардкожен в `config.py` —
      вынести в `.env`, это единственная правка кода бота на этом шаге).
      `year` необязателен и по умолчанию равен текущему UTC-году — именно
      это и позволяет держать URL фида константой в конфиге бота.
- [x] Строгая валидация query-параметров на всех эндпоинтах: неизвестное
      имя и повтор параметра — 422, а не тихо проигнорированный фильтр
      (`?type=` вместо `types=` отдавал бы весь год, `?types=a&types=b` —
      только `b`). Полный справочник API — в `README.md`.
- [x] Генерация кеша — фоном: `/health` отвечает сразу после старта
      (попарные поиски сближений могут занимать минуты), регенерация по
      расписанию. Версия генератора хранится **в кеше**, не в uid:
      смена версии перегенерирует кеш, а uid остаются детерминированными
      от сущности события — иначе каждое обновление логики меняло бы все
      uid и плодило дубликаты в upsert-таблице бота.
      Прошлые годы сервису не нужны: бот анонсирует только предстоящие
      события, поэтому фоном генерируются лишь текущий год (+ следующий
      в декабре). После bump'а версии генератора прошлые годы штатно
      выпадают из `coverage` без регенерации — контракт покрытия делает
      это явным для клиента, это не баг.

## Этап 5. Docker и публикация

- [x] Dockerfile сервиса (эфемериды — слоем образа, кеш — volume
      `/data` через `SKYEVENTS_CACHE`, чтобы volume не затенял
      эфемериды); CI сервиса собирает и публикует образ в GHCR по пушу
      в `main` (после зелёных тестов), теги — `latest` + `sha-…`.
- [x] Свой `docker-compose.yml` в этом репозитории: `image` из GHCR,
      `pull_policy: always`, кеш — named volume `skyevents-cache`,
      подключение к external-сети `astronet`, порт наружу не публикуется
      (бот ходит на `http://skyevents:8000`). Не единый compose с ботом,
      а раздельные — чтобы релиз одного не пересоздавал контейнер
      другого. `depends_on` между compose не работает и не нужен: бот
      переживает недоступность сервиса на своём кеше.
- [x] Деплой сервиса — свой SSH-джоб в его CI (после публикации в GHCR):
      `git pull` + `docker compose pull` + `up -d`. Деплой бота не
      трогается. `astronet` создаётся на хосте один раз вручную.

## Этап 7. Малые тела

Считаются не по эфемеридам DE440s, а двухтельным движением по
орбитальным элементам MPC (`skyevents/mpc.py`: разбор формата MPCORB и
построение кеплеровой орбиты; `sun + orbit` дальше ведёт себя как
обычное тело). Скорость — 0.1 с на объект за год поиска.

- [x] Противостояния ярких астероидов. Момент — **максимум солнечной
      элонгации**, а не равенство эклиптических долгот, как у планет в
      `planet_sun`: при заметном наклонении это разные моменты (у
      Паллады, i=34.9°, они разнесены на 2.4 суток), и фид считает
      именно максимум элонгации — совпадение с ним 5 мин против 2.4
      суток у долготного определения. Он же и физически «то самое»
      мгновение: ближе всего, ярче всего, всю ночь над горизонтом.
      Порог публикации — блеск < 10ᵐ по системе H–G с реальным фазовым
      углом (у Паллады 7.3° — это 0.4ᵐ, ровно на границе). Порог
      выверен по фиду: он публикует Ирену 9.3 и Фидес 9.5, но не
      Партенопу 10.0 и Нису 10.1. Блеск округляется до десятой
      **до** сравнения с порогом, а не после: клиент фильтрует по тому
      числу, которое мы отдали, и объект, записанный как «10.0», не
      прошёл бы собственный контракт README (десятая и так тоньше
      точности модели H–G). Состав 2027 совпал с фидом один в один
      (13 событий), в 2026 у нас два лишних объекта (Эвномия 9.9,
      Дембовска 9.8) — модели блеска расходятся в последней десятой,
      это принято (как пограничные случаи в сближениях).
      Каталог — все нумерованные астероиды с H ≤ 8.6 (242 объекта,
      ~50 КБ), закоммичен: сервис остаётся офлайн. Элементы стареют,
      поэтому в тестах живёт проверка свежести эпохи (3 года), а в
      README — команда обновления. Путь назначения у неё аргументом, а
      не `>`-редиректом: шелл обнуляет файл до запуска, и оборванная
      закачка уничтожила бы закоммиченный каталог. Битая строка
      каталога пропускается с warning'ом (генераторы идут подряд, и
      одна строка не должна унести с собой затмения), но пустой
      каталог — ошибка: «файл сломался» не должно выглядеть как «в
      этом году нет ярких астероидов».
- [x] Кометы (`skyevents/comets.py`, `skyevents/generators/comets.py`).
      Реализовано по принятым ниже решениям; состав 2026 — 8 комет ярче
      12ᵐ (при 10ᵐ — 5, как и предсказывал расчёт), перигелий совпадает с
      элементом T до секунды, 10P/Tempel даёт перигей и пик в один день
      разными типами, фрагменты 141P/-A/-D — разными slug'ами, 2P/Encke
      не порождает краевого артефакта. Принятые решения:
      - источник — `CometEls.txt` MPC (160 КБ), качается **в рантайме**
        в `SKYEVENTS_DATA` фоновым циклом (`refresh_loop` в `api.py`)
        не чаще раза в неделю; генератор читает только локальный файл,
        поэтому тесты остаются офлайн (фикстура из нескольких строк в
        `tests/data/`). Сети нет → работаем на прошлой копии, файла
        нет → кометных событий нет, и это надо логировать явно;
      - кеш: год должен перегенерироваться **по возрасту записи**
        (`years.generated_at`), а не только по её отсутствию — иначе
        комета, открытая после генерации года, в него не попадёт;
      - события: перигелий (берётся из поля T элементов, поиск не
        нужен), перигей (`find_minima` по расстоянию от Земли) и пик
        блеска (`find_minima` по `m = g + 5·lg Δ + 2.5·k·lg r`), порог
        **12ᵐ** (~10 комет в 2026; при 10ᵐ их 5);
      - три отдельных типа событий, не один с `kind`: у 10P/Tempel в
        2026 перигей и пик блеска попадают на одну дату, а uid —
        `тип:тела:дата`, и они бы схлопнулись в одно событие;
      - slug — из обозначения и **с учётом фрагментов**: в каталоге
        одновременно живут 141P, 141P-A и 141P-D с одинаковым packed-
        обозначением `0141P`;
      - пик блеска искать на окне с запасом и отбрасывать минимумы на
        краю: у 2P/Encke (перигелий 2027-02) минимум по окну 2026 года
        выпадает ровно на 1 января — артефакт границы, не событие.
- [ ] (Опционально) Сближения астероидов с планетами и Луной — фид их
      публикует («Conjunction of Venus and Ceres»); нужен отдельный
      порог, как у `close_approaches`.

## Риски

- **Состав событий не совпадёт с фидом один в один**: in-the-sky
  добавляет события с ручной курацией (яркость, наблюдаемость). Принять:
  наш состав определяется списком генераторов и порогами; полный дифф
  этапа 0 покажет, чего заметно не хватает.
- **Точность**: моменты сближений зависят от того, считаем ли
  геоцентрически. Считать геоцентрически (как фид), допуски зафиксировать
  тестами.
- **Два репозитория — контракт надо версионировать**: изменения формата
  ответа API сопровождать версией (заголовок или `/v1/` в пути с самого
  начала), чтобы деплой сервиса не ломал бота.
- **Размер эфемерид** (~32 МБ) раздувает образ — приемлемо; при
  необходимости сузить период через `python -m jplephem excerpt`.
